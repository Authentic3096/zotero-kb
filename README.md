# Zotero 文献知识库

**把 Zotero 里的文献，变成 AI 能秒查、能按页精读、并且越用越准的本地知识库。**

它解决的问题很具体：文献存在 Zotero 里，但 AI 用不上 —— 它不知道你库里有什么、
读了也记不住哪篇讲过什么、更不知道你**试过哪些方法、哪条路走不通**。

这个项目把「找文献 → 存进 Zotero → 拆成知识库 → 喂给 AI → 记下经验」整条链路打通，
**全程在本机完成**（只有"搜新文献"那一步需要联网）。

---

## 一、它到底能做什么：一条闭环

```
① 找文献  →  ② 抓进 Zotero  →  ③ 拆成知识库  →  ④ 喂给 AI  →  ⑤ 经验回流
```

⑤ 的经验会**回流到 ④**：下次检索时，"验证过有效"的文献自动排到前面 ——
这是整套系统里唯一会自我改进的一环。

| 环节 | 你会看到什么 | 实现上最关键的一点 |
|---|---|---|
| **① 找文献** | 对话里直接出现候选表：标题（**可点开看原文**）、作者、年份、摘要、关键词、被引、是否开放获取 | 搜索与呈现**全在对话里**，不用来回切窗口 |
| **② 抓进 Zotero** | 勾选完就抓，进度一条条报（"第 2/4 篇…"）；权威元数据与 PDF 一起到位 | **抓取交给 Zotero 自己**——校园网出口 IP、机构订阅、自带的 PDF resolver 全部天然生效，不用下载再手工拖 |
| **③ 拆成知识库** | 每篇变成可检索切片 + 按页正文 + 图表注；面板里能看到全库体检报告 | **Zotero 全文缓存优先、PyMuPDF 兜底**；坏文本有准入判据，拿不准的交本地小模型仲裁 |
| **④ 喂给 AI** | 一句话搜到相关文献；要细节时按页读正文；图注表格单独可查 | **13 个 MCP 工具 + 4 个资源**；先搜后读、按页取，不把整篇塞进上下文 |
| **⑤ 经验回流** | 你说一句"这篇的方法试了，不行"，之后它自己会沉下去 | **经验真的改变检索排序**（权重公式在 `offline/schemas.py`）——这是整套系统唯一会自我改进的部分 |

## 二、为什么比"把 PDF 丢给 AI"强

| | 直接把 PDF 丢进对话 | 只用 Zotero 自带的搜索 | **本方案** |
|---|---|---|---|
| 上下文成本 | 每次重传，长文直接爆 | — | 建库一次，之后**按需取页** |
| 能搜到的范围 | 只能搜你此刻记得的那篇 | 只匹配标题/作者/年份，**搜不到正文内容** | 关键词 + 语义**两路混合**，中英文都行 |
| 精度 | 模型现场读，读到哪算哪 | — | 返回**带页码的原文片段**，可回溯核对 |
| 跨对话记忆 | 换个对话就忘 | — | 经验层持续累积，**影响下次排序** |
| 数据去向 | PDF 上传到云端 | 本地 | **全本地**：切片、向量、模型都在你自己机器上 |

几个具体场景：

- **"我库里有没有讲过 XX 的？"** → 混合检索直接给带页码的片段，不用自己回想是哪篇。
- **"这几篇的方法有什么区别？"** → AI 按页读正文 + 查图表注，而不是靠摘要猜。
- **"这个方法我试过了吗？"** → 经验层回答"试过、什么条件、有效还是无效、为什么"。
- **"这个方向还有哪些新文献？"** → 对话里搜 → 列候选（带摘要与被引）→ 勾选 → Zotero 抓进库 → 立刻可搜。

> 不接 AI 也能用：管理面板（Tk）+ Zotero 插件（自动切片、分类建议、知识库权重列）
> 独立可用。接 AI 的部分走标准 **MCP**，任何支持 MCP 的客户端都能接（DSH 是一条
> 已经打通的路径，配置见 [`INSTALL.md`](INSTALL.md) 第 6 节）。

## 它解决什么问题

文献存在 Zotero 里，但 AI 用不上——不知道你的库里有什么、读了也记不住哪篇讲过什么。
这个项目让 DSH 能：

1. 一句话搜到相关文献（关键词 + 语义两路，中英文都行）
2. 按需读某一篇的方法细节，带页码
3. **记住用过的经验**：上次试过哪几篇、哪个有效、哪个因为初值敏感失败
4. 越用越准：验证有效或标重点的文献，下次检索自动排前
5. **找新文献并直接抓进库**（v0.24.0）：搜 → 列候选表 → 你勾选 → 进 Zotero，不用下载再手工拖

> **图标**：**一本立着的书 + 一道斜掠而过、串着知识节点的椭圆轨道**。
> 书 = 文献；轨道上的**圆环节点** = 知识之间的关联；轨道在**节点**和
> **封面左上角**处断开，让位给它们（透视上的前后关系）。
> 在 `zotero-plugin/icon.svg`；工具栏小图标是同意象的简化版。改完用
> `tools/preview_icon.py` 出图验收（16/32/48/96 四档 + 浅色/深色主题）。
> **设计稿 `tools/icon-design.pptx` 是 PowerPoint 原生形状**（可直接拖），
> 几何常量在 `tools/make_icon_pptx.py` 顶部；`make_icon_svg.py` 由**同一份
> 常量**生成插件用的 SVG —— 改设计只改那一处，两种格式不会漂移。
> **管理面板顶部**另有一张头像与署名（`tools/assets/avatar.png`）。

## 获取文献：搜 → 列候选（可点开看）→ 勾选 → 抓进 Zotero

前面几节都是"读已有的"，这一节是"找新的"。

**先说清一件最容易误解的事：抓取不是本项目做的，是 Zotero 自己做的。**

```
DSH（我）        web_search 找候选 → 核 DOI（标题对不上就扔）
   │             → 列成表（标题是可点开的链接，用户自己点开看原文）
   │             → 勾选框让用户点选
   │  kb_acquire（只传勾中的 DOI）
   ▼
本地服务 8765    任务队列
   │
   ▼
Zotero 插件      Translate.Search 抓元数据 → 建条目 → 找可用的 PDF
                 → **走本地模型给分类建议 + 打标签**
                 （全在 Zotero 进程内，用**你这台机器当下的网络身份**）
```

### 为什么必须让 Zotero 去抓

| 理由 | 说明 |
|---|---|
| **网络身份** | 请求从 Zotero 进程发出 → **校园网出口 IP、学校订阅的刊、出版社会话全都天然生效**。等同你自己在浏览器里点下载，只是工具替你点了 |
| **不用手工拖** | 抓完直接是一条带附件的条目。用户的原话："不要下载下来手动拉" |
| **元数据更准** | 走 Zotero 的翻译器生态（实测走 "DOI Content Negotiation"），比解析搜索结果网页可靠 |
| **resolver 更全** | `Zotero.Attachments.addAvailableFile` 是 Zotero **自带**的"查找可用的 PDF"，自带 DOI 落地页 → 条目 url → 开放获取源 → PMC → 自定义 resolver 一整套。自己写爬虫不可能比它全 |

### 怎么用

对 DSH 说「帮我找几篇某主题的文献，我要下载」即可（触发 `zotero-acquire` 技能）。

**整件事都在 DSH 对话里发生** —— 搜索、候选表、勾选、抓取进度、最终结果。

```
你：帮我找几篇「某主题」的文献

DSH：搜到 3 篇候选（**点标题能打开原文页**）：

     | # | 标题（点开看原文） | 作者 | 年份 | 出处 | 关键词 | 全文 |
     |---|---|---|---|---|---|---|
     | 1 | [某综述](https://doi.org/10.xxxx/yyyy) | Wong | 2024 | 某期刊 | 甲、乙、丙 | ✅ 开放获取 |
     | 2 | [某实测研究](https://doi.org/10.xxxx/zzzz) | King | 2026 | 某期刊 | 丁、戊 | 🔒 需订阅 |
     | 3 | [某方法研究](https://doi.org/10.xxxx/aaaa) | Li | 2023 | 某期刊 | 己 | 🔒 需订阅 |

     ← 你点标题去浏览器里看原文

     ☑ 1. 某综述（Wong 2024）        ← 在 DSH 界面里勾选框勾选
     ☐ 2. 某实测研究（King 2026）
     ☐ 3. 某方法研究（Li 2023）           [确认]

你：（勾了 1，点确认）

DSH：抓这一篇。Zotero 那边不弹确认框 —— 你刚才的勾选就是确认。
     → 进行中 0/1，正在处理 10.xxxx/yyyy      ← 每隔几秒报一次
     → 完成：1/1 篇入库，1 篇带 PDF
     → 补抽知识库…（新文献立刻能被 kb_search 搜到）
```

**几个关键点**：

- **列表里标题是链接** → 你点开自己看原文，再决定勾不勾。
  （摘要不硬塞进对话：实测不少刊三方都没有摘要，而链接一定能用。）
- **勾选就是确认**，勾完直接抓，**不再问第二次**。
- **进度是实时念出来的**：MCP 工具是一次调用阻塞到返回的，抓一篇要十几秒 ——
  不拆开的话那段时间对话里一片空白，你分不清是在跑还是卡死了。

也可以直接调工具：

```python
# 候选文献的"值不值得看"信息：摘要/关键词/主题/OA/被引
kb_paper_info(dois="10.xxxx/yyyy, 10.xxxx/zzzz")

# 1~2 篇：一次调用直接拿结果
kb_acquire(dois="10.xxxx/yyyy")

# 3 篇以上：派发 + 轮询（DSH 会把进度念出来）
kb_acquire(dois="10.xxxx/yyyy, 10.xxxx/zzzz", wait=False)   # → job_id
kb_acquire_progress(job_id="aq...")                          # → 进度 / 最终报告

# 先试试抓不抓得到（一个字节都不写库）
kb_acquire(dois="10.xxxx/yyyy", dry_run=True)
```

| 参数 | 说明 |
|---|---|
| `dois` | 勾中的 DOI，逗号/换行分隔；整条 `https://doi.org/...` 也认 |
| `wait` | `False` = 立刻返回 job_id（**3 篇以上、或想报进度时用**）；默认 `True` 阻塞到抓完 |
| `collection_id` | 目标分类；**默认 0 = 存到你在 Zotero 里当前选中的分类**（与浏览器连接器一致） |
| `find_pdf` | 是否顺带找 PDF（默认是） |
| `dry_run` | 只解析元数据、**不写库** |
| `reindex` | 入库后自动补抽知识库（默认是；**只对 `wait=True` 生效**） |

### 插件侧的行为

- **默认不弹确认框**（`zotero-kb.acquireConfirm` 默认**关**）—— 搜索/列表/挑选
  本来就在 DSH 对话里完成，再弹一个 Zotero 模态框会把一次连贯的对话中断成两个界面。
  想要"落盘前再看一眼"的人可以在**插件设置 → 从 DSH 导入文献**里把勾打开。
- **落库后走一遍本地模型的分类建议**（`zotero-kb.acquireAutoClassify` 默认开）：
  模型给每篇推荐分类和标签，**一个汇总框一次问完**（不是每篇弹一次 ——
  抓 5 篇弹 5 个模态框，点完"添加"还要连点 5 次）。三选一：
  **全部应用 / 逐篇确认… / 跳过**。「逐篇确认」保留原有的完整能力
  （看理由、也能让模型重判）。
- 只**新建**条目；**绝不改**你已有的条目（唯一例外是会跳过库里已有的 DOI）。
- 结束时一个进度窗报"几篇入库 / 几篇带 PDF / 几篇跳过"。
- **一次导入多篇时，不会逐篇弹分类建议框**（否则抓 10 篇会被 10 个框连击）。
  条目落在目标分类里；想补分类建议：选中后右键 →「分类建议（本地模型）」。

### 边界（这条线不许挪）

| | 做不做 | 为什么 |
|---|---|---|
| **用你已有的访问权限**（从你自己的机器发请求；校园网 IP、学校订的刊、你自己浏览器的登录态） | ✅ **可以，这正是这个功能的价值** | 等同于你自己在浏览器里点"下载" |
| **绕过付费墙**（改 URL 骗计费、影子图书馆、盗用凭证、伪造订阅身份） | ❌ **绝不做** | 版权与合规 |

线划在**"这个请求是不是以你自己的合法身份发出的"**上。

### 抓不到 PDF 时

按这个顺序退，不要跳：

1. **浏览器连接器**（最有效）：在出版社页面点 Zotero 图标。它跑在你的浏览器里、
   带着你的登录态，能过的站点比进程内抓取多。**中文文献（知网/万方）基本只有这条路。**
2. **已知直链**：`tools\fetch-pdf.ps1` 下载（**会验 `%PDF` 文件头**），
   再用 `kb_attach(item_key=..., path=...)` **挂到条目上** —— 不用手工拖。
3. 都不行 → 如实说没找到，不绕。

### 自检

链路每一环在不同进程里，断了都只显示一句"抓取失败"。所以有个分段自检：

```powershell
& "<项目目录>\.venv\Scripts\python.exe" -X utf8 "<项目目录>\tools\check_acquire.py"
& "...\python.exe" -X utf8 "...\tools\check_acquire.py" --live   # 加一段真抓（dry_run，仍不写库）
```

它会逐段报"知识库位置 / 本地服务 / 插件版本与轮询 / DOI 归一化 / 参数校验 / 干跑"，
**先失败的那一环就是问题所在**。

> **"Zotero 没开"和"插件没在轮询"是两回事**，修法也不同 ——
> 插件状态文件**每 30 秒才写一次**，Zotero 刚关掉时它看着还是新的。
> 要判 Zotero 本身在不在，打它的连接器端口：
> `Invoke-RestMethod http://127.0.0.1:23119/connector/ping` ——
> 有响应（哪怕 404）就说明活着，连不上才是没开。`kb_acquire` 内部就是这么判的，
> 所以它现在会直接说"Zotero 没在运行"而不是"插件没在轮询"。

> **升级注意（这一条踩过坑，务必看清）**：改完 `bootstrap.js` 之后，
> **运行中的 Zotero 不会自动用上新代码**。两种装法对应两种生效方式：
>
> | 装法 | 改完源码怎么生效 | 风险 |
> |---|---|---|
> | **侧载代理**（`extensions\zotero-kb@authentic3096.github.io`，内容是源码目录路径） | **重启 Zotero 即生效，不用重新打包** | 项目目录不能移动 |
> | **真 xpi**（`extensions\zotero-kb@authentic3096.github.io.xpi`） | 必须**重新打包 + 重新安装** | ⚠ **最容易坑人的一种**：profile 里那份 xpi 会一直是旧的，你以为改了、其实跑的还是老代码 |
>
> **开发期推荐侧载代理**：`tools\sideload_plugin.py install`（需先完全退出 Zotero）。
>
> **每次验证前先确认跑的是哪一版**（能省掉一整轮白测）：
>
> ```powershell
> & "<项目目录>\.venv\Scripts\python.exe" -X utf8 "<项目目录>\tools\check_acquire.py"
> # 第 3 段会报「插件版本 X.Y.Z」以及状态文件多久没更新
> ```
> 没重启时 `kb_acquire` 会明确报"插件是 0.23.0，要 0.24.0 以上" ——
> 看到这句就去重启 Zotero，**不是**重装插件。

## 知识库放哪 / 怎么跟着 Zotero 走

默认位置：**<Zotero 数据目录>\zotero-kb\**。Zotero 数据目录是从它的
prefs.js 读出来的（extensions.zotero.dataDir），所以你改过也没关系。

### 在插件里看与改

设置面板 → **知识库位置**：

`
知识库位置
  <知识库>
  [刷新] [打开这个目录] [迁移到 Zotero 数据目录]
`

「迁移」做的事：**先备份** → **复制**（不是移动，旧目录保留）→ **校验**
（条目/切片/向量/经验数必须一致）→ 写 kb-location.json。
校验不过会中止并告诉你，**不会**让你丢数据。迁移完要**重启知识库服务**才生效。

### 命令行等价操作

`powershell
python tools\migrate_kb.py            # 干跑，只说会做什么
python tools\migrate_kb.py --apply    # 真迁移
python tools\check_abs_paths.py       # 迁移前检查索引里有没有绝对路径
`

### 为什么迁移是安全的

实测确认：**索引里不存文件路径**（papers/、ulltext/ 都按 Zotero key 命名，
路径由 KB_DIR 推算）。所以搬目录不会破坏索引。
	ools\check_abs_paths.py 可随时复核。

> ⚠ 迁移前**必须先停服务**：index.db 是 WAL 模式，服务在跑时复制会漏掉
> -wal 里的新数据（本机在读 Zotero 库时踩过同样的坑）。

## 关于"把知识库同步到 Zotero 的同步"

**这件事做不到**，原因是 Zotero 的同步机制设计如此。查了它的源码
（chrome/content/zotero/xpcom/sync/syncLocal.js）：

`javascript
let dir = Zotero.Attachments.getStorageDirectoryByID(obj.id).path;
`

文件同步**只针对"数据库里有附件条目的文件"**，也就是 storage/<itemID>/ 下
那些。知识库目录不在它的管辖范围内 —— 放在 Zotero 数据目录旁边也**不会**被同步。

硬要接上去只有一条路：**把每个 .md 挂成 Zotero 附件**。代价是：

| 代价 | 数量级 |
|---|---|
| 新增附件条目 | 101 篇 × 2（摘要+正文）+ 3730 切片 ≈ **数千个** |
| 首次上传 | 145 MB 到 WebDAV（坚果云） |
| 每次重建索引 | 一变就要同步，流量大、还可能卡住同步队列 |

所以**没有做**这个开关，改成两个真能用的替代方案（默认关闭）：

### 替代一：同步到目录（推荐）

让坚果云/OneDrive 客户端去同步知识库目录。

`
设置面板 → 知识库同步 → 方式：同步到指定目录
                        目标：<你的同步盘>\zotero-kb
                        [立即同步一次]
`

### 替代二：执行命令

已经有 rclone / robocopy 的话直接填命令（会显示输出）：

`
方式：用命令同步
目标：rclone sync "<知识库>" nutstore:zotero-kb
`

> 用的是"复制 + 覆盖"而不是镜像删除 —— 万一目标目录里有别的东西，
> 镜像（
obocopy /MIR）会把它删掉，这不该由我们代劳。

## 模型后端：本机 Ollama 或任意 OpenAI 兼容 API

**在 Zotero 插件的设置面板里配**（编辑 → 设置 → 文献知识库），这是唯一配置源。

### 两种后端

| 后端 | 适合 | 需要 |
|---|---|---|
| **Ollama**（默认） | 完全离线、不花钱、数据不出本机 | 装 Ollama + `ollama pull qwen3:4b-instruct` |
| **外接 API** | 不想本地部署；或机器跑不动；想用更强的模型 | 一个 API Key（可能还要充值） |

**换后端不难，因为主流服务用的是同一套协议**（业界叫 "OpenAI 兼容"）——
DeepSeek、通义千问、ChatGPT、Kimi、智谱、硅基流动、OpenRouter 全都算，
区别只是 **服务地址 + 模型名 + Key** 三样东西，代码一行不用改。

### 设置面板里的三步（v0.16 起）

```
① 用哪家      [DeepSeek（深度求索） ▼]   ← 选了自动填下面两项
② 模型名      deepseek-chat
③ API Key     sk-...
              [测试并保存]              ← 点一下就知道通不通
```

预设了 8 个：DeepSeek / 通义千问 / ChatGPT / Kimi / 智谱 GLM /
硅基流动 / OpenRouter / 其它自建。选完只要再粘一个 Key。

**「测试并保存」会真的调一次模型**，并把失败原因说成人话：

| 情况 | 提示 |
|---|---|
| Key 不对 | `HTTP 401：... is invalid` + 「去服务商后台重新复制一个」 |
| 余额不足 | 「账户余额不足 —— 去服务商后台充值」 |
| 模型名错 | 「多半是模型名写错了，或该模型不支持 JSON 输出」 |
| 地址错 | 「注意有些服务地址要带 /v1，模型名要和服务商文档一致」 |
| 网络不通 | 「连不上 https://… —— 检查网络」 |
| Key 粘进中文 | 「你的 key 里有 2 个非英文字符（中文…），已自动去掉」 |

> 为什么专门做这一块：**用户第一次配 API 十有八九会填错**，
> "填错了会怎样"比"填对了能跑"更影响体验。
> 本机为此写了 6 个错误场景的自动验证，每一条都要求报错是**人话 + 可操作**。

**分类和打标签不需要很强的模型** —— `deepseek-chat`、`qwen-plus`、
`gpt-4o-mini` 这类便宜的就够（一次分类几百 token）。

**地址不填也能推断**（填了模型名就够）：

```
deepseek-chat      → https://api.deepseek.com/v1
qwen-max           → https://dashscope.aliyuncs.com/compatible-mode/v1
gpt-4o-mini        → https://api.openai.com/v1
moonshot-v1-8k     → https://api.moonshot.cn/v1
glm-4              → https://open.bigmodel.cn/api/paas/v4
llama-3.3-70b      → https://api.groq.com/openai/v1
```

自建的（vLLM / LM Studio / one-api）选「其它 / 自建」后手填地址，
注意有些服务要带 `/v1`。

> ⚠ 同一批地址写在**两处**：`offline/judge.py` 的 `KNOWN_BASE_URLS`
> 和 `zotero-plugin/settings.js` 的 `KB_API_PRESETS`。不一致会导致
> **设置界面显示一个地址、实际请求打到另一个**。
> `python tools\check_api_presets.py` 会对比两边（已接进打包检查）。

### 这套协议覆盖谁

凡是提供 `/chat/completions` 的都能用：OpenAI、DeepSeek、通义千问（dashscope
兼容模式）、Moonshot/Kimi、智谱 GLM、Groq、OpenRouter、SiliconFlow、
以及自建的 vLLM、LM Studio、Ollama 的 `/v1` 层。

**不支持**：Anthropic Claude、Google Gemini 的原生协议（它们不是 OpenAI 格式）。
要用得先过一个转换网关（如 one-api / LiteLLM）。注意 OpenRouter 上有
Claude / Gemini，走 OpenRouter 就能间接用到。

### 配置怎么流到各处

```
Zotero 设置面板（唯一配置源）
   │
   ├─ 新文献分类时随 /classify 一起发 → 服务端落盘（<知识库>/llm-config.json）
   │    ⚠ v0.16 起：这三个字段**直接透传**给 judge，不只依赖落盘
   │    （落盘在"用户清空 key"和"落盘失败"两种情况下会用到旧配置，
   │      报的错和用户填的对不上 —— 本机踩过）
   │
   └─ 点「测试并保存」→ 落盘 + 真调一次模型

管理面板 / 命令行 / 定时任务
   └─ 读同一份 <知识库>/llm-config.json（所以它们也用同一套配置）
```

**为什么要有"同步"按钮**：插件设置的配置是随请求走的，而管理面板、命令行
这些入口不经过插件。点一次同步，它们就都统一了，不会出现"插件用 A、面板用 B"。

> `kb/llm-config.json` 里有 API Key，**不要**提交到版本库或分享出去
> （已在 `.gitignore` 里排除）。

2. **知识库不用重建** —— 它在 Zotero 数据目录下，
   跟着你原来的同步方式走；
3. **经验层和权重在 `<知识库>\index.db`** —— 那个文件要单独备份，
   重新索引**不会**恢复它们；
4. 装完插件记得**完全退出 Zotero 再打开**（关窗口不算）。

#### 关于按钮名与字体（2026-10 交互打磨）

几个改动的理由，都是用户实际反馈的：

| 改动 | 为什么 |
|---|---|
| 「更新索引（增量）」→ **「手动更新」** | "增量"是给写代码的人看的词；用户只关心"我新加了文献，点它更新" |
| 「全量重建」→ **「全部重建」** | 同上 |
| **文献选择改成独立弹窗** | 原来把 `作者 年份 · 标题 [KEY]　［分类］` 拼成一整行塞进下拉框 —— 标题长短不一时既对不齐、又改不了宽度，长的被截断短的留空白。拆成表格后每列可拖宽、表头可排序、窗口可拉大 |

| 底部日志 | 长任务实时输出、可停止；不会卡界面 |

### 文献清单 INDEX.md

知识库根目录有一份 **`INDEX.md`**，是**给人看的**目录：

```markdown
| 文献 | 类型 | 全文 | KEY |
|:---|:---:|:---:|:---|
| Zhang W. 2025 · 面向小样本的迁移学习方法研究 | 学位论文（1 笔记） | ✓ 82k | `<KEY>` |
| Du C. 2025 · 基于对比学习的表征压缩方法 | 期刊 | ✓ 49k | `<KEY>` |
```

为什么需要它：知识库里的文件按 Zotero key 命名（`22X9PMR6.md`），唯一但
**完全认不出是哪篇**。检索时靠 `kb_search` 就够了，但想"看看库里都有什么"
时没有入口 —— `papers\` 目录点开是一堆 8 位代号。

「更新索引」之后会自动重建，也可以手动 `python tools\make_index.py`。

**检索结果和面板里也都显示可读名**（`作者 年份 · 短标题 [KEY]`），
不用再对着 `22X9PMR6` 猜是哪篇。

> ⚠ 为什么不干脆用可读名当**文件名**：库里已经有重名 —— 3 篇同名
> 《X射线检测分析技术在文物保护修复中的应用》、2 篇同名
> "Magnetic Dipole Moment Determination…"。用标题当文件名会互相覆盖，
> **仍然必须靠 key 区分**。所以文件保持 key 命名（也保证迁移后路径可推算），
> 可读名只做显示。

## Zotero 插件（v0.14.x）

装在 Zotero 里，做两件事：**新文献自动进知识库** + **本地模型给分类建议、一键应用**。

### 装

见 [`INSTALL.md`](INSTALL.md) 的「第 3 步：装 Zotero 插件」
（含打包命令，以及为什么必须完全重启 Zotero）。


> **装完必须完全重启 Zotero**：bootstrapped 插件在运行中更新**不会**重跑
> `startup()`，代码只在加载时读一次。这是最常见的"装了没用"原因。

设置会自动完成——插件探活时从服务端取 token（带 `Origin` 的浏览器请求不会拿到，
见 `online/localserver.py` 的 `/health`）。不需要手工填任何东西。

### 运行环境（v0.14 新增）

设置面板里多了**「运行环境」**一节，三个框 + 「浏览…」按钮：

| 项 | 含义 | 留空时的默认 |
|---|---|---|
| 项目目录 | 代码和 `.venv` 在哪（含 `offline\`、`online\`） | 自动探测（找到 `tools\gui.py` 的那个目录） |
| Python 解释器 | 跑脚本用 | `<项目目录>\.venv\Scripts\pythonw.exe` |
| Ollama 程序 | 本地模型（可选） | `%LOCALAPPDATA%\Programs\Ollama\ollama.exe` |

点「保存并检测」会把配置推给本机服务（落盘到 `<项目>\kb-location.json`），
并立刻回一份**逐项报告**：找到了什么、是否可用、该改哪个框。

> **为什么不自动装 Python**：查实过 Zotero 插件**能**起外部进程
> （`Subprocess.sys.mjs` / `nsIProcess`），也能下载解压。但代价是要处理
> 约 300 MB 的下载、断点续传、失败回滚 —— 为了省用户"选一次文件夹"不值得。
> 所以选了"显式配置 + 自动探测"，改起来直观、出错能说清原因。

**这三个位置互相独立，谁也不能由谁推算** —— 这是踩过的坑：老代码让
「项目目录」= 「知识库位置的上一级」，知识库一搬到 Zotero 数据目录，
就算出 `<Zotero 数据目录>`，那里没有 `.venv`，
于是管理面板报「找不到 Python 环境」。现在报错会把**找的是哪个路径**说清楚。

### 用

在 Zotero 里保存/新建一篇文献，约 2-5 秒后：

1. 弹出 `正在把新文献送进知识库…`
2. 接着弹出**分类建议窗**（推荐一个分类 + 几个标签 + 置信度 + 理由）
3. 点「应用」→ 归入该分类 + 打上标签；也可选「调整…」或「跳过」

#### 右键菜单：分类建议（本地模型）

在 Zotero 里**右键任意文献** → 「分类建议（本地模型）」，
和「发送到 DSH」并列。这是给"看到某篇觉得它该归哪儿"的那一刻用的 ——
比去管理面板再查出这篇的 key 快得多。选中多篇会逐篇串行问。

弹窗里有三个按钮：

| 按钮 | 作用 |
|---|---|
| **应用** | 归入该分类 + 打上标签（真的写回 Zotero） |
| **调整…** | **跟模型对话**：写一句你的判断，它据此重判 |
| 跳过 | 什么都不做 |

「调整」是这么用的 —— 模型只看标题和摘要，而你可能有别的信息：

```
推荐分类：分类 B   置信 98%
理由：文献聚焦于神经网络层的表示学习与评估…

点「调整…」→ 输入：这篇应该归到「分类 A」
→ 重新判断：分类 A   置信 100%
   理由：用户明确指出应归入…符合该分类的延伸应用场景
```

> 实现上不是"让模型自由发挥"：**分类名照样必须落在已有分类里**
> （`judge.classify_item` 的校验不变），你的意见只影响它选哪个，
> 不影响可选范围。同一份实现也被管理面板的「调整建议」调用，
> 所以两边口径一致。

#### 右键菜单：补全元数据（本地模型）

用 Zotero 抓文献时识别失败很常见：**日期 / DOI / 卷 / 期 / 页码留空**。
这些值其实**就印在 PDF 首页**，只是 Zotero 没抓到。右键 → 「补全元数据（本地模型）」，
它读前两页，按**规则优先、模型兜底**给你一份建议清单。

每条建议都带四样东西，缺一不可：

| 显示 | 为什么必须有 |
|---|---|
| **字段 → 建议值** | 要写什么 |
| **〔规则·高置信〕/〔模型·低置信〕** | 值是怎么来的。规则是从固定格式（DOI 正则、`第 37 卷`、`pp. 765-770`）里抠的，出处明确；模型会**编**（实测它把参考文献里的 DOI 当成这篇的 DOI），所以模型给的一律标低置信 |
| **原文证据（第几页 + 片段）** | 你唯一能核对的依据。"这个 37 是这篇的卷，还是参考文献里别人的卷"—— 只看值看不出来，看片段就一眼 |
| 模型证据定位不到时的提示 | 模型复述的原文如果没能在正文里找到，会明说"请自行核对 PDF" |

弹窗里有三个按钮：

| 按钮 | 作用 |
|---|---|
| **全部应用** | 按清单全部写入（默认全勾选就是这个意思） |
| **逐条确认…** | 一条一个对话框，**每条一个勾选框、默认勾上**，可以取消；也能点「后面的都不用了」中断 |
| 跳过 | 什么都不做 |

三条硬规矩（写死在代码里，不是"尽量遵守"）：

1. **只写这几个字段**：`date` / `DOI` / `volume` / `issue` / `pages`，
   外加**作者（`creators`）**——作者原先也在禁写之列，后来单独开放，
   但只在「逐条确认」这条路上开，而且只在**条目一位作者都没有**时才写
   （整份名单，不做部分合并；`setCreators` 是整表替换语义，见代码注释）。
   弹窗里会逐行列出抽到的姓名、以及"原文只列了前 N 位（et al./等）"的警示。
   **标题永远不写**。
   ⚠ **批量**（多选「一键采用」）仍然不写作者：那是一次确认写 N 篇、
   没有逐条证据可核，而作者是错一个字符就毁掉引用的字段。
2. **只填空、不覆盖**：只对"当前为空"的字段给建议；写之前还会**再查一次**，
   中途被你手工填上的字段直接跳过并说明（作者的复查用 `getCreators()` ——
   `getField('creators')` 恒为空，拿它查等于没查）。
3. **不点确认就什么都不写**：服务端只出建议（`/metafill` 是纯读接口），
   写回只发生在插件侧、而且只写你在弹窗里勾过的那几条。写完会回报
   "成功几项 / 跳过几项 / 你取消了哪几项 / 失败几项"。

> ⚠ 已知会出错的一处：`页码`这一项，模型有时会把**该页的页码**（例如某页页脚
> 印着的 `564`）当成页码范围填进来。这种建议会额外标一句「⚠ 可能是单页页码，
> 请核对」。低置信的 `页码` 建议请务必对着证据核一眼。
>
> 字段改了以后**知识库里的索引不会自动跟着变** —— 要让新值进检索/权重，
> 顺手右键「重建知识库条目（这一篇）」（几秒一篇）。

## 检索是怎么做的（以及为什么这么做）

调过几轮才定下来，记在这里免得以后又改回去：

1. **中文按字索引，但召回用短语**
   SQLite FTS5 的 `unicode61` 把连续中文当成一个 token，所以「偶极子」搜不到
   「机器学习模型」。最早的做法是把查询拆成单字用 AND 连——**实测太严**：
   「机器学习模型」六个字全中的只有 1 条，而库里明明有 15 条相关。
   改成 OR 又太松：召回 15 条但「无关领域无损检测」排到了第 2
   （只因它含"反""演"两个字）。**最终方案**：`build_match_phrases` 把中文连续段
   作为短语查询（要求这些字相邻出现），命中不足再退到单字 OR 兜底。

2. **打分的权重按子串长度平方**
   命中「反演」（连续两个字的词）比命中孤立的「反」值钱得多。这一条
   就把无关领域那篇从第 2 压到了第 4。

3. **稀有度加权**
   `term_df` 表记录每个词元出现在多少切片里。「偶」「极」这种字区分度高，
   「磁」「方」满库都是。检索时按 IDF 加权，避免常用字主导排序。

4. **融合按"证据强度"而不是数排名**
   纯 RRF 有个坑：一篇文献命中 5 个弱相关块，能靠数量压过只命中 3 个强块的
   文献（实测过）。所以融合时乘两个因子：该路的质量分（IDF 覆盖率 / 余弦相似度），
   以及同一篇里第 n 个块的**位置衰减**。

5. **每个条目最多只用 3 个块参与打分**
   否则块多的文献凭空占便宜。

6. **经验权重乘在融合分上**
   权重只影响排序，不影响召回——该出现的必须出现。

7. **两路的质量分必须先各自归一化**
   关键词路的覆盖率能差 6 倍，向量路的余弦却挤在 0.63-0.66（区分度仅 5%）。
   不归一化时，向量路会因为绝对值大而主导排序——实测「机器学习模型」的
   第一名被带偏成《基于统计学习的信号分离方法》。现在各路先做组内
   min-max 拉到 0-1，再按 0.65（关键词）/ 0.35（向量）加权：
   修完后第一名回到《基于统计学习的信号分离方法》，
   且 **top-8 全部与"机器学习模型"真相关**（模型压缩、知识蒸馏、
   对比学习建模…），不再出现无关领域的噪音。

8. **结构化字段走"展示 + 可选筛选"，不动排序**
   Zotero 条目的 `extra` 里有一部分是**知网写进去的结构化字段**（中图分类号、
   来源库、收录标签、中文译名、学位专业…）。它们由 `offline/extrafill.py`
   解析成知识库的 `item_extra` 表（`offline/convert.py` 每次构建时维护，
   条目删除靠外键级联），并在三处用起来：

   | 用在哪 | 形态 |
   |---|---|
   | 检索命中 | 每条命中带 `structured`（中图分类号 / 来源类型 / 收录标签 / 中文译名 / 学位专业）—— 英文标题的文献常常有中文译名，据此能确认"是不是用户说的那篇" |
   | 筛选 | `kb_search` 可传 `source_kind`（journal/thesis/conference，也认中文）、`publication_tag`（EI / 北大核心 / CSCD…）、`clc`（分类号，支持 `TP39` 这样的大类前缀） |
   | 展示 | `kb_item` 给提纯后的 `structured` + 原样照录的 `extra_fields`；tldr 资源多一行"结构化字段"；`kb_stats` 报覆盖率 |

   **为什么不拿它给召回加权**（这是刻意的取舍）：加权动的是排序，而排序目前
   只有零星的人工核对、没有回归集 —— 改坏了不会当场暴露。筛选只在明确说
   "只要 EI 的""只要学位论文的"时改变结果集，不传参数时连一次 SQL 都不多跑，
   对既有检索行为**零影响**。
   ⚠ 只有 `extra` 里有这些字段的条目才筛得到（本机 100 篇里带知网结构化字段
   的是 39 篇），筛不到**不等于**不符合 —— 空结果时工具会明说这一点。
   `download`（下载计数，含义无法确认）只原样留存，**不参与任何判断**。

## 经验层：知识库为什么"越用越准"

三层结构，同一个库里：

| 层 | 内容 | 谁写 |
|---|---|---|
| 原文层 | PDF 正文、高亮标注、笔记 | 离线管道（只读） |
| 结论层 | 元数据、摘要、分类 | 离线管道（只读） |
| **经验层** | 试过哪几篇、方法是什么、效果如何、失败原因、重点标记 | **DSH 当场追写 + 小模型事后补** |

`experience` 表只追加（每次尝试一条，历史永不丢），`item_weight` 表攒战绩：

```
权重 = 1.0 + 3×重点标记 + 人工分 + 2×有效 + 1×部分有效 + 0.5×无效
最终分 = 检索融合分 × (1 + ln(权重))
```

三个刻意的选择：

- **失败也算正分（0.5）**：知道"这条在这类问题上不行"本身有价值，
  只是不如"有效"值钱。
- **取对数**：有效 1 次是 2.10，3 次是 2.95 —— 递减增长，不让某一篇垄断结果。
- **重点标记给 3 分**：你手动标一次，抵得上它被验证有效一次半。

**怎么用起来**：`kb_search` 每次都会把加权后的排序和相关经验一起返回。
所以效果是——你用一次，库就厚一分，下次直接看到，不需要你额外做什么。

**谁来记**：

- **当场记**：DSH 有明确结论时调 `kb_experience_add`。快、准，但要 DSH 记得调
  （靠 `SKILL.md` 里的纪律约束）。
- **事后补**：`offline/learn.py scan` 扫 DSH 会话记录（`~/.dsh/sessions/*.jsonl.zstd`），
  先用关键词粗筛候选片段，再让本地小模型抽成结构化条目。**只写到
  `kb/inbox/pending.jsonl` 待确认**，你过一眼才入库——小模型会编，
  不能让未经验证的内容污染检索排序。

## 边界与已知限制

- **不写 Zotero**。本机 Zotero 9.0.6 的本地 API 是只读的（写入要 Zotero 10+，
  见 <https://www.zotero.org/support/dev/web_api/v3/local_api>）。
  也绝不直接改 `zotero.sqlite` —— 那要处理 `synced`/`version`/同步队列，
  写错会污染并同步到 zotero.org。AI 的产出写在 `kb\papers\` 或会话目录。
- **数据库访问必须走 `Searcher` 的接口**，不要在外面直接 `s.conn.execute(...)`。
  MCP 工具会在不同线程被调用，裸访问绕过串行化锁，并发下会报
  `InterfaceError` / `OperationalError`，甚至**静默丢写**（实测 20 条只进 13-17 条）。
  读用 `s.read()` / `s.read_one()`，写用 `s.write()` / `s.write_returning_id()`。
  相关回归测试：`tests/test_threading.py`（并发读 + 并发写 + 混合操作）。
- **经验类查询必须返回契约里的字段**，否则检索结果会静默丢字段（见下文"已修"）。
  契约常量是 `online/server.py` 的 `EXPERIENCE_ROW_FIELDS`；
  回归测试 `tests/test_experience_fields.py`（临时库、23 项）会对三个行来源
  （`experience_for_item` / `related_experience` / 裸 `SELECT *`）分别断言字段齐全。
  加测试时验证过：把 `evidence` 从 SELECT 里拿掉，该测试会报红并退出码 1。
- **不做 OCR**。本机 110 篇 PDF 全部有文字层（已实测），所以没接 OCR。
  以后遇到扫描件，该条目会明确标记 `fulltext_missing`，不会静默返回空。
- **笔记里的内嵌截图不搬运**，只留一行说明（图片在 Zotero 里看）。
- **知识库不是实时同步**：Zotero 里改了内容要跑 `1-convert.cmd` 或调 `kb_reindex`。
- **网页类条目**（4 篇）没有全文，只有元数据。
- **`judge.py` 的打标签结果写在 `meta` 表**（`ai_tags:<key>`），
  不覆盖你在 Zotero 里手工打的标签。
- **小模型默认用 4B**（`qwen3:4b-instruct`）。装了 1.7B 之后 `ollama list`
  的顺序会把 1.7B 排前面，代码里已显式优先 4B —— 抽经验这类活儿 4B 明显更靠得住。
  想换用 1.7B：设环境变量 `KB_LOCAL_MODEL=qwen3:1.7b`。

### 已修：经验查询漏列字段（2026-10-02）

**症状**：`kb_experience_query` / `kb_search` 返回的经验记录里，某些字段恒为空。
（`evidence` 恒为 `null`；按 `item_key` 查询时 `items` 恒为 `[]`。）

**根因**：**写入端是好的**（数据库里列有值），是**查询显式列举列名时漏了字段**。
`SELECT *` 的分支（`kb_experience_query` 不带 query/item_key/tag 时）不受影响，
所以只在按关键词或按文献检索时暴露。

| 漏掉的列 | 影响 | 位置 |
|---|---|---|
| `evidence` | 检索结果与单篇档案 md 里都看不到"依据" | `searcher.py` ×2、`converter.py` ×1 |
| `item_keys` | 按 `item_key` 查询时 `items` 恒为 `[]` | `searcher.py` → `experience_for_item()` |

**已修**：上述四处 SELECT 补齐；`converter.render_experience` 增加 `  - 依据：...` 输出行。
另在 `online/server.py` 增加**契约常量 + 运行时防御**：

- 常量 `EXPERIENCE_ROW_FIELDS`（11 列）作为单一事实来源，组装器所需字段都在里面；
- `kb_experience_query` 组装前会核对每行字段，缺列时**直接返回带 `missing` 的错误**
  而不是静默给出 `null`/空数组；
- 测试 `tests/test_experience_fields.py` 对三个行来源分别断言（用临时库，不动真实索引）。

**防复发**：`online/server.py` 的响应组装器要读
`id / created_at / asked / context / method / outcome / reason / evidence / item_keys / tags / source`
共 11 个字段，**凡新增或修改经验类 SELECT，都对照 `EXPERIENCE_ROW_FIELDS` 核对一遍**，
并跑一次 `tests/test_experience_fields.py`。
注意 `server.py` 里非 item_key 分支对 `items` 有默认值（`"[]"`），
而 `item_key` 分支**没有**默认值 —— 漏列会直接表现为空数组，不易察觉。

**注意**：改完必须**重启 DSH / 重连 MCP** 才生效 —— Python 服务进程已导入的模块不会热重载，
在旧进程里验证会看到字段仍是 `null`/空，容易误判为没修好。
库层可这样自查（绕过 MCP 进程）：

```powershell
& <项目目录>\.venv\Scripts\python.exe -X utf8 -c `
  "import sys; sys.path[:0]=[r'<项目目录>\offline', r'<项目目录>\online']; `
   from searcher import Searcher; s=Searcher(); `
   print([(r.get('evidence') is not None, r.get('item_keys')) for r in s.experience_for_item('S8AS73XB', 3)])"
```

> 顺带一个排查提醒：`converter.render_experience()` 依赖连接带 `row_factory=sqlite3.Row`
> （由 `schemas.connect()` / `init_db()` 设置，`convert.py` 走的正是这条）。
> 若在外部用裸 `sqlite3.connect()` 调它，会报 `TypeError: tuple indices must be integers`——
> 那是调用方式问题，不是 render 本身的 bug。

**该测试自身曾有的假阳性（已修）**：它原本用 `SV._SEARCHER = None` 清
`kb()` 的缓存实例，但 `server.py` 里的变量名是 **`_searcher`（小写）**，
`INDEX_DB_OVERRIDE` 更是一个不存在的名字 —— 两处赋值只是新建了模块属性，
**缓存根本没清**。后果：一旦 `kb()` 已被调用过，`[5]` 段的 monkeypatch 就失效、
会连到**真实索引库**去查那个只存在于临时库里的 key，查不到时 `count`/`items`
断言本该失败，但真实库恰好也有同结构数据时它会**照样通过**。
现在已改成 `SV._searcher = None`，并加了一条「确实连的是临时库
（evidence 是临时值）」的断言兜住这种情况。

### 已修：测试数据残留会继续影响排序（2026-10-02）

**症状**：清理过自检数据后，`list` 看起来已经干净（没有测试经验了），
但某篇文献的权重仍是 2.79、备注还写着"自检标记"、`pinned` 还亮着 ——
**检索排序继续被测试数据影响**。

**根因**有两层：

1. 删除测试经验时只回滚**该经验涉及的**权重，而测试标记
   （`pinned` / `manual` / `note`）是**另一条路径**（`kb_weight_set`）留下的，
   不会跟着回滚；
2. `clean --test-data` 在"没找到测试经验"时**提前 return**，
   后面的残留清理代码永远走不到。

**已修**：`clean` 不再提前返回；新增 `--orphan-weights` 专门清残留。
判据是「有 `pinned`/`manual`/`note`，却**没有任何经验引用它**」——
因为这三个字段只有人工操作会写，`kb_experience_add` 不动它们。

```powershell
# 删测试经验（会回滚其权重），并提示是否还有残留
tools\kb_admin.py clean --test-data
# 清零"没有经验支撑"的权重残留
tools\kb_admin.py clean --orphan-weights
```

清理后建议核对一下：`tools\kb_admin.py list` 里不该出现 `自检`/`验收`/`测试`
字样的经验，也不该有 note 为"自检标记"的权重行。
`offline\maintain.py check` 的 [3] 段现在会自动检查这两类残留。

### 已修：Zotero 10 的 WAL 让读者一直读到过时数据（2026-10-02，最隐蔽的一个）

**症状**：通过 Zotero 10 的本地 API 把 33 篇文献重新归类、并删掉两个重复分类后，
跑 `convert.py` 重建，**知识库里却还是旧分类**。更迷惑的是：全量重建也不变。

**根因**：`ZoteroReader` 做快照时只 `shutil.copy2(zotero.sqlite)`，
**没拷 `-wal` / `-shm`**。而 Zotero 10 起启用了 **WAL 模式** ——
新写入先落在 `zotero.sqlite-wal` 里，主库文件可能长时间不更新。
于是 reader 读到的永远是"上一次 checkpoint 之前"的旧库。

官方文档（[Zotero 10 for Developers](https://www.zotero.org/support/dev/zotero_10_for_developers)）
专门警告过这一点：

> **WAL mode is enabled**. If your plugin or external tool reads zotero.sqlite
> directly … it must account for the `-wal` and `-shm` files — copying the main
> database file alone can produce a stale or inconsistent snapshot.

**修法**：快照时把三个文件一起拷（先 `-wal`、再主库），并先清掉旧快照的残留
`-wal`（否则 SQLite 会把上一次的日志当成新库的一部分去恢复）。

> 也试过用 `sqlite3.Connection.backup()`（理论上更干净），但 Zotero 开着时它会被
> 库锁**卡死**（实测挂住 5 分钟以上），所以退回文件级拷贝。拷贝瞬间若 Zotero 正在写，
> 理论上可能取到不一致状态；对只读建索引可以接受，下一轮增量会自愈。

**这个坑最坑的地方**：它会让"核对"也一起骗你 —— 我写过一个脚本对比"Zotero vs 知识库"的
分类，报告"0 条不一致"，但那个脚本**也走 reader**，所以两边都在读同一份过时快照。
修好后真核对才归零。

**排查提示**：以后凡是"Zotero 里明明改了、知识库没跟上"，先怀疑 WAL。
另一个同源症状是**附件增删检测不到**（Zotero 改附件/分类都不动 `items.version`）——
为此给 `items` 加了 `collections_sig` 列（分类+标签指纹），增量和它一起比。


### 已修：另两处会"静默产生错数据"的地方（2026-10-02）

**① 所有条目的 `fulltext_chars` 都是 0。**
`Item.fulltext_chars` 由 `fulltext_pages` 求和得来，而 `convert.py` 拿到正文后
只放在局部变量里，**从没回填 `item.fulltext_pages`**。
后果：`kb_item` 与 `http://…/item/tldr/{key}` 显示"全文 0 字符"、`kb/papers/*.md`
里写 0 页 —— 看着像索引坏了。实际 `chunks`/`vectors`/正文文件都是好的，
**检索不受影响**，属数据准确性问题。修好后全库合计约 279 万字符。

**② 向量可能被整表误删。**
"换模型就清理旧向量"原本写成
`DELETE FROM embeddings WHERE model <> 当前模型`。只要 `meta.embed_model`
是**空串**（而库里其实存着向量），这个条件对**所有**行成立 → 全部删掉，
检索的向量路归零、要等约 65 秒重算。
而那个空串又是另一半代码造的：manifest 里写过
`args.embed_model if vector_count else ""`，`--no-vectors` 跑一次就会写空。
现在改成：只有 meta 里明确记着**另一个模型名**时才清理；manifest 从库里读实际值。

> 如果你哪天发现 `kb_search` 的 `vector_used` 变成 `false`、
> `kb_stats` 的 `vectors` 变 0：跑一次 `1-convert.cmd`（不加 `--no-vectors`）
> 就会补回向量（3706 个约 65 秒）。
