# 知识库的层级结构

这篇讲**现在这套东西是怎么组织的**：知识库里有哪些文件、各自由谁生成、谁在读、
能不能删。要装与用的步骤见 [../INSTALL.md](../INSTALL.md)，架构总览见
[../ARCHITECTURE.md](../ARCHITECTURE.md)。

## 一、总览

知识库是一个目录（默认在 Zotero 数据目录下的 `zotero-kb\`）：

| 层 | 位置 | 谁写 | 谁读 | 删了会怎样 |
|---|---|---|---|---|
| 索引 | `index.db` | 构建（`offline/convert.py`）、经验与权重写入 | 检索、面板、MCP | **不能删**（唯一的库） |
| 原始层 | `mineru\<KEY>\` | MinerU 解析（可选组件） | 构建时读 `pages.json` 作为正文来源 | 可重建（要重跑解析） |
| 正文层 | `fulltext\<KEY>.md` | 构建 | 摘要生成、按页取正文、MCP 的 full 资源 | 可重建 |
| 档案层 | `papers\<KEY>.md` | 构建 | 面板与右键菜单的「完整档案」 | 可重建 |
| 视图层 | `views\<KEY>.*.md` | `offline/kbviews.py`（构建收尾、面板可重生成） | 「打开知识库」各级、MCP 的 tldr 资源 | 可重建 |
| **归档层** | `trash\<KEY>\` | 两段式删除（`offline/trash.py`）：条目**进 Zotero 回收站**时把这一篇的视图 / 档案 / 正文 / MinerU 产物 + 行快照搬进来 | 从回收站**还原**时按快照装回去 | **删了就还原不了**（要腾空间就等它在 Zotero 里被彻底删除，那时才是真没用） |
| 清单 | `INDEX.md`、`MANIFEST.json` | 构建 | 人看 / 插件读摘要 | 可重建 |

除 `index.db` 之外，上面每一层都是**派生物**：删掉重跑一次构建即可（**`trash\` 例外** —— 它的价值就是"删之前的那一份"）。

> **完整的目录与文件清单以面板「知识库结构」页为准**（`tools/panels/common.py::KB_FILE_SPEC`，
> 那一页把每个条目的"是什么 / 占多大 / 能不能删"都写清了）。这里只讲**内容层级**，
> 运行时的 `inbox\` `logs\` `.cache\` 与几个 `.txt` / `.json` 不在此列，免得两处漂。

## 二、各层做什么

### 原始层：`mineru\<KEY>\`

MinerU 的原始产物：`markdown.md`（全文）、`structured_content.json`（**按页**的块结构）、
`middle_json.json`、`images\`（切出来的图）、`pages.json`（我们渲染的逐页文本）、
`meta.json`（指纹、页数、耗时）。

- `structured_content.json` 是**按页**的（`pages[].page_idx` + `blocks[]`），
  块类型有 `doc_title` / `paragraph_title` / `text` / `equation` / `table` /
  `chart` / `image` / `header` / `footer` / `page_number` / `ref_text` 等。
- 页眉页脚页码由 MinerU **自己标出来**，构建时直接丢掉（比用正则猜可靠）。
- 公式是 LaTeX，构建时包成 `$$…$$` 写进正文 —— 这样**公式也能被检索命中**。

装了 MinerU 才有这一层；没装就不存在（正文改由 Zotero 缓存或 PyMuPDF 提供）。

### 正文层：`fulltext\<KEY>.md`

带 `## p.N` 页码锚点的逐页正文，是检索切片、按页取正文、生成摘要的统一入口。
每页末尾会附上**这一页的图注与表格**（见第四节）。

### 档案层：`papers\<KEY>.md`

元数据 + 结构化字段（知网写入的中图分类号、收录标签等）+ 摘要 + 笔记与高亮标注，
外加一段「分节纲要」概览（有了纲要之后自动补上）。**不含**完整正文 —— 那是正文层的事。

### 视图层：`views\<KEY>.*.md`

「打开知识库」里能选的那几级，都是这个目录下的现成文件：

| 级别 | 文件 | 内容 |
|---|---|---|
| 摘要与要点 | `views\<KEY>.tldr.md` | 元数据、结构化字段、摘要、AI 要点、笔记要点 |
| 分节纲要 | `views\<KEY>.outline.md` | 按章节的要点（第五节），每节带页码范围 |
| 完整档案 | `papers\<KEY>.md` | 见上一节 |
| 按页正文 | `fulltext\<KEY>.md` | 见上一节 |
| 图注与表格 | `views\<KEY>.figures.md` | 把散在各页的图注与表格按页汇总成一份 |
| 权重与经验 | `views\<KEY>.weight.md` | 检索权重、重点标记、人工加减分、全部使用经验 |

这些 md 旁边还有同名的 `.html`（生成时把 `$$…$$` 转成 MathML），
Zotero 右侧栏的「知识库预览」分区读的就是它 —— 不需要额外插件或字体。

## 三、正文从哪来

构建时按下面的顺序取正文，取到哪个算哪个，**按篇**决定（一篇失败不影响别的）：

| 顺序 | 来源 | 说明 |
|---|---|---|
| 1 | **MinerU**（装了才走） | 逐页文本来自 `structured_content.json`；页眉页脚已丢、公式是 LaTeX |
| 2 | Zotero 全文缓存 | Zotero 自己已经抽好的全文（多数期刊 PDF 都有） |
| 3 | PyMuPDF | 前两条都没有时逐页 `get_text()` 兜底 |

- 走了哪条路记在 `items.fulltext_src`（例如 `mineru-basic` / `zotero-cache` / `pymupdf`），
  MANIFEST 里也会统计；MinerU 解析失败的那几篇**按篇回落**，不会把整轮降级。
- 面板「PDF 解析」页可以看每一篇的解析状态、补缺失的、全库重解析。
- 增量：正文或解析器变了才重建这一篇（MinerU 按 PDF 指纹 + 档位判断）。

## 四、图表这条链（两个来源，别混）

图表相关的东西来自**两处**，职责不同：

1. **图注与表格的结构化抽取 —— `offline/figures.py`，用 PyMuPDF，全程不调模型。**
   构建时逐页扫文本，按 `图 / 圖 / Fig. / Figure + 编号` 之类的规则认出图注，
   表格按文本布局识别。结果：
   - 存进 `figures` 表（面板与 `kb_figures` 检索用它，`items.n_figures` / `n_tables` 是计数）；
   - 由 `converter.figures_for_page()` 渲染到正文里**那一页的末尾**（标着「本页图注」）；
   - 汇总成 `views\<KEY>.figures.md` 那一级。
   **这一路与正文来源无关**：正文用 Zotero 缓存还是 MinerU，图注都是这么抽的。

2. **MinerU 的产物里也带表格与图。**
   `structured_content.json` 里有 `table` / `chart` / `image` 块，`images\` 里是切好的图。
   现状：本机 MinerU 4.0.10 的产物里，这些块**没有图片路径字段**（`img_path` 为空），
   所以构建时没有把它们渲染成正文里的图片行；但**表格块的文字**（HTML 形式）
   会照常进正文。

两点结论：

- 现在库里看到的图注，**全部**来自第 1 条（PyMuPDF 那一路）——
  MinerU 4.0.10 的 `chart` / `image` 块里没有图注字段，图注只能靠 PyMuPDF 抽。
- 表格**按正文来源分工，只留一路**（避免同一张表在正文里出现两次）：
  - 正文来自 **MinerU** 的篇：表格用 MinerU 的（已经在逐页正文里，HTML 形态），
    构建时**跳过** PyMuPDF 的表格抽取；
  - 正文来自 **Zotero 缓存 / PyMuPDF** 的篇：表格用 PyMuPDF 抽的（那是唯一来源），
    照旧渲染进「本页图注」块并汇总到「图注与表格」那一级。

⇒ `figures` 表里，图注覆盖全部文献；表格只覆盖"正文不是 MinerU"的那些篇，
  查询时不要把"没有表格"当成"表格抽取坏了"。

## 五、全文与摘要之间的那一级：分节纲要

知识库是「摘要 →（中间层）→ 全文」三级：摘要只有几百字，全文动辄几万到几十万字，
中间这一层的跨度靠它补上。由 `offline/digest.py` 生成：

> **它依赖模型**（本地 Ollama 或「模型接入」里配的外部 API）——
> 没有可用的模型就没有这一层，只有摘要与全文两级。
> 一节一次调用，一篇学位论文要几分钟，所以生成是显式动作（Zotero 里右键 / 面板按钮 / 命令行），
> 而不是随手打开就能有。

- **按 MinerU 的标题块切节**（`doc_title` / `paragraph_title`），页眉页脚页码丢掉；
- 带标题的节一律保留；没有标题的碎片才并进相邻节；
  参考文献、致谢、附录**跳过不展开**（占位一行）；
- 每节让本地模型写 2~4 句 + 3~6 条关键点，要求公式写成 LaTeX（这样也能排版）；
- 每节带页码范围（`p.5–p.9`），想细看就按页取原文；
- 按**节指纹**缓存：正文没变的节不重跑，改一章只重跑那一章；
- 落地：`meta.ai_outline:<KEY>`（结构化）+ `views\<KEY>.outline.md`（人读）。

生成入口（四个，后三个是同一套服务端实现的三个外壳）：

1. **Zotero 文献列表里右键 →「连接到本地模型」→「生成分节纲要」**（最常用：看到
   「分节纲要」那一列是 ✗ 的那一刻就能点）。多选会逐篇**串行**跑，已经有纲要的
   自动跳过，跑完汇总「已生成 N 篇、跳过 M 篇（已有纲要）、失败 K 篇」；
   跑的过程中同一菜单里会出现「停止生成纲要」。
2. 管理面板「AI」页的「生成纲要」按钮；
3. `python offline/digest.py <KEY>`；
4. `python offline/digest.py --missing`（补全库）。

后台实现只有一份：Zotero 右键那条路是 `POST /digest` →（服务端线程）
`digest.build(..., should_stop=…)`。**读端（MCP / 菜单 / 窗格）只读现成的**，
不现场生成 —— 一篇学位论文要几分钟。

## 六、检索与权重

- 检索在 `online/searcher.py`：关键词（SQLite FTS5）与向量两路先各自排序，
  再用 RRF 融合（关键词 0.65 / 向量 0.35，RRF_K = 60，含质量分与位置衰减）；
- 融合分再乘**权重乘数**，权重来自 `offline/schemas.py`：
  年份基础分（0.95~1.05，按当前年份实时算、不落库）+ 重点标记 +3.0 + 人工加减分
  + 经验（有效 +2.0 / 无效 +0.5 / 部分有效 +1.0），最后取 `1 + ln(原始权重)`；
- **完整公式、各档取值与例子见 [../ARCHITECTURE.md](../ARCHITECTURE.md) 的
  「权重的算法（精确公式）」**（这里不重复，免得两处漂移）；
- 经验来自 `experience` 表：每次「用某篇的方法做了什么、结果如何」记一条，
  这是整个系统里唯一会自我改进的一环。
