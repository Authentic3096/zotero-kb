# 知识库层级设计（重排方案，2026-10-05）

> **这份是方案，不是已实现状态。** 现状与目标都写清了，每一节末尾有「怎么验」。
> 写法沿用本项目既有约定：单一权威 + 派生可重建 + 每层说清"谁写谁读、能不能删" +
> 结构表（`KB_FILE_SPEC`）与文档同步。
>
> 背景：2026-10-05 把全库正文换成了 MinerU 解析的结果之后，同一篇文献出现了
> **3~4 份正文派生体**，用户原话是「现在知识库就算又多了一级：MinerU 的全文 md
> 含内置图片，知识库的架构我还是很不满意」。这份文档就是回答"该怎么排"。

### 现在的问题（按严重程度）

1. **图片层缺失**：MinerU 已经切好了公式与图表（94 篇 186 MB），但没有一层
   "这篇的图在哪" —— 检索命中图注时给不出图，将来给 VLM 看图也没有入口。
2. **同一篇有 3~4 份正文派生体，且没说清谁权威**：`papers/*.md`（含正文首段）、
   `fulltext/*.md`（逐页）、`mineru/<KEY>/markdown.md`（原始全文）、
   `views/*.card.md`（每页首段）。改一处、别处不知道。
3. **`papers` 与 `views/tldr` 内容重叠**（摘要/元数据各出现一遍）。
4. **摘要级信息有断层（已修一半）**：`judge.py summarize --write` 把 AI 要点写进
   `meta` 表的 `ai_summary:<key>`，但**没有任何地方读它** —— 2026-10-05 全库重跑
   94 篇摘要时才发现（本文件同一轮已把 AI 要点渲染进 `views/*.tldr.md`）。
5. **检索没有层级意识**：`chunks` 里全是正文切片，摘要/图注/表格/笔记混在同一路
   排序里，权重一样。用户想要的"大模型酌情读哪一级"目前**只靠人在菜单里选**。
6. `mineru/<KEY>/markdown.md` 与 `fulltext/<KEY>.md` 的关系没写死：
   前者是"原件"，后者是"我们加工的权威正文"，但没有任何地方说明，
   新人（或半年后的我）很容易直接改前者。

## 二、目标层级（五层，各层职责单一）

```
① 原始层  kb/mineru/<KEY>/          MinerU 原件：markdown.md / structured_content.json
                                    / middle_json.json / images/ / pages.json / meta.json
   ── 不可变（除重解析）；可整层删除；**只有 convert 读它**（读 pages.json）

② 正文层  kb/fulltext/<KEY>.md      **唯一权威正文**：## p.N 页锚点 + 公式 $$ + 图注
   ── 由 ① 的 pages.json 生成；检索切片、按页取正文、摘要生成都读它

③ 档案层  kb/papers/<KEY>.md        元数据 + 结构化字段 + 笔记 + 高亮 + 经验索引
   ── **不含正文首段**（那是正文层的事）；给人"一眼看全这篇有什么"

④ 视图层  kb/views/<KEY>.{tldr,card,figures,weight}.md
   ── 纯派生（随时重生成）；tldr = 摘要级入口（含 AI 要点），card = 完整档案视图

⑤ 图片层  kb/figures/<KEY>/         真图片（图表/示意图），从 ① 的 images/ 里**挑**出来
   ── 图注与图片一一对应；供"给我看图"与将来的 VLM 路线
```

### 各层的关键约定

| 约定 | 说明 |
|---|---|
| **单一权威** | 正文只认 `fulltext/<KEY>.md`；`mineru/markdown.md` 是**原件**，不许手改、不许直接喂检索 |
| **可删性** | ①②③④⑤ 全部可删可重建（每次构建/`maintain.py views` 都重生成）；只有 `index.db` 不能删 |
| **图片引用** | 正文层**保留**一行 `![图注](../mineru/<KEY>/images/page_3_chart_5.jpg)`（用户 2026-10-05 拍板：留，方便索引），但**切片时剔除图片行**（`chunker` 加一条过滤）—— 这样"读 md 时图在"、"检索文本干净"两件事都成立 |
| **图注与图片的对应** | 图注文字进正文层（能检索），图片文件进图片层（能看），两边用 `page_N_kind_M.jpg` 的文件名对齐 |
| **AI 产物** | 摘要/标签/AI 要点一律落在 `meta` 表 + 渲染进 `views/tldr`（**不许只写不读**，见现状问题 4） |

## 四、检索分层（借鉴 EKR 的"层级偏置"）

外部调研里最值得抄的是 EKR 的这条：**检索时对"抽象层"和"细节层"给不同先验，
并按问题类型切换**（它的 `abstract-biased` / `entity-biased` 两种加权）。

落到我们已有的 RRF（0.65 FTS + 0.35 向量 + 经验权重）上，加**第 4 路信号**：

```
final = rrf_score × weight_multiplier × layer_prior(query_kind, layer)
```

| 查询类型 | 判据（toy 但够用） | 先验方向 |
|---|---|---|
| 「这篇讲什么 / 综述」 | 含"讲什么/介绍/综述/总结" | `abstract`/`tldr` ↑，`body` 不变 |
| 「怎么做 / 方法 / 实现」 | 含"方法/怎么/实现/步骤/算法" | `body` ↑、`figcaption` ↑ |
| 「数据 / 参数 / 结果」 | 含"数据/参数/数值/结果/多少" | `table` ↑、`body` ↑ |
| 默认 | — | 全部 1.0（等于现状） |

**纪律**：先做成**开关**（`KB_LAYER_PRIOR=1`），默认关；用真实查询跑一组对比
（同一批 20 个查询，比较 top-5 命中与人工判断），确认有改善再考虑默认开。
不许"凭感觉改排序"——本项目吃过这个亏（让模型给切片打相似度分，判错 60%）。

## 五、经验闭环 2.0（借鉴 Asterism + Literature Mapper）

现状：`item_weight` 是"一次性加分"（有效 +2、重点 +3…），然后 `1+ln(raw)`；
经验条目只有 `effective/ineffective/partial` 三态 + `item_keys`。

| 借鉴点 | 落地做法 | 收益 |
|---|---|---|
| Asterism 的 Hebbian 权重（用得多、用得近 → 越高） | `item_weight` 增加"最近一次使用时间 / 使用次数"，权重里加时间衰减项 `e^(−Δt/τ)`（τ=180 天，可配） | "上个月验证过有效"比"两年前有效过"更有分量 |
| Literature Mapper 的语义边 | 经验条目加 `relation ∈ {supports, contradicts, extends}` + `direction`（哪篇支持哪篇）+ 证据行 | 从"经验列表"变成"方法—结论图"，检索时可按关系过滤 |
| Asterism 的结论 | 权重的作用是**歧义下的决断力**（相关度相同时有权重的胜出），而不是压过相关度 | 提醒我们：`weight_multiplier` 不该主导排序 —— 这也是**不改现有权重口径**的理由（用户 2026-10-05 拍板不改公式，只改文案） |

## 七点五、中间层：分节纲要（2026-10-05 已实现）

用户原话：「还是知识库层级的问题，**全文太长，现有的摘要还太短，怎么加中间的一层级**」。

现在的四级（摘要 → **纲要** → 全文，加上档案/视图）与体量：

| 层 | 文件 | 体量（实测一篇 5 页期刊论文） | 用途 |
|---|---|---|---|
| 摘要级 | `views/<K>.tldr.md` | 几百字 | 判断"要不要深读" |
| **中间层（新）** | `views/<K>.outline.md` | **约 2600 字 / 8 节** | 先看"有哪几节、每节做什么"，再决定读哪一节 |
| 全文 | `fulltext/<K>.md` | 12639 字 | 精读（按页取） |

### 怎么切的（`offline/digest.py`，新模块）

- **按 MinerU 的标题块切**（`structured_content.json` 里 `doc_title` /
  `paragraph_title`）—— 比从 markdown 里猜标题行可靠；页眉页脚页码块照旧丢掉；
- **带标题的节一律保留**（纲要的价值就是保住原文节结构）；只有"没有标题的碎片"
  才并进相邻节（阈值 120 字，本机踩过 400 字阈值把「1 引言」吃掉的坑）；
- **参考文献/致谢/附录跳过**（占位一行"（略）"，不调模型）—— 这类节动辄几千字；
- 超长节按段落再切（`（续 N）`）；节数上限 24（超了合并相邻节）；
- **每节带页码**（`p.5–p.9`）→ 想细看就 `kb_fulltext(page_from=5, page_to=9)`。

### 成本与增量

- 每节一次模型调用（节内正文截断 5000 字）；实测 **约 10~22 秒/节**，
  一篇 5 页论文 8 节 **33 秒**；一篇 90 页学位论文 16~20 节约 5~7 分钟；
- **按节指纹缓存**（`sha1(标题+正文[:2000])[:6]`，存在 `meta.ai_outline:<KEY>`）：
  正文没变的节不重跑 —— 改一章只重跑那一章；
- 生成入口：面板「分类建议」页 →「生成纲要」；`python offline/digest.py <KEY>`；
  `--missing` 补全库。**不写进索引、不改排序**（用户已明确"检索分层算了吧"）。

### 落地位置

```
meta.ai_outline:<KEY>          结构化 JSON（节 / 页码范围 / 要点 / 指纹）
views/<KEY>.outline.md         给人读的纲要（kbviews 的第 2 级，紧跟摘要级）
zotero-kb://item/outline/<KEY> MCP 资源（读一下就能看到纲要）
```

⚠ **不许在 MCP 资源/菜单里现场生成**：一篇学位论文要几分钟，随手点一下就卡住 ——
生成只走按钮/CLI，读端只读现成的（`kbviews._render_outline`）。
